## 3. SELECTED: C

## 4. Selection rationale

1. **Lowest migration risk with the strictest constraint compliance.** C's app change is one line (`key={location.search}` in `ToolPage`); it never rewrites the URL, so the "URL が必要以上に更新され続けない" / no-per-keystroke-rewrite constraints hold by construction instead of by debounce compromise (B). Existing tests are safe for verifiable repo reasons: the 5 `Tool.test.tsx` files render prop-less without a Router and are typechecked — C's hook reads `window.location.search` (empty in jsdom → defaults), so the existing 386 tests pass unchanged; A's required `onShareStateChange` prop would have broken those same 5 files at typecheck.
2. **Correct responsibility split with the least machinery.** Tool-specific state (zod schema, defaults, restore recompute, Share button) lives entirely in each tool folder; common URL mechanics (envelope `v`, base64url/JSON transport, total `parse`/`serialize`) live in framework-agnostic `packages/core`; the only React binding is one small router-agnostic hook in `packages/ui`. No global store, no debounce, no `useSyncExternalStore`, no app-side schema knowledge — fewer moving parts than A and far fewer than B, and it satisfies "React 内部 state そのものの永続化" / "巨大万能 JSON object" / "app 側 schema 手書き管理" bans.
3. **Best testability + type safety at the shared boundary.** All failure handling is pure and unit-testable in core (malformed base64url/JSON/version/schema → defaults; unknown keys stripped; missing keys defaulted; round-trip; defaults-equal → no Share); state types are zod-inferred (`z.infer`), zero `any`/casts; e2e needs no config change (clipboard permissions already granted in `playwright.config.ts:8`).
4. **Scaling to 100–200 tools costs nothing shared.** A new tool = `state.ts` (5–15 lines reusing its own `logic.ts` constants) + hook adoption + one Share line — exactly the "added by the tool itself, never by the app" property the task demands, and the generated registry / `generate-registry.mjs` / `tool-loader.ts` are untouched.

## 5. Required adjustments (to plan C)

All minor; none change the design shape.

1. **ToolPage key source (clarify):** `ToolPage.tsx` must obtain `const { search } = useLocation()` from react-router-dom and render `<Tool key={search} />` — the plan's `location.search` shorthand must not be mistaken for `window.location.search` (which would never change under the router).
2. **Default-equality check (implementation detail):** `serializeToolState` returns `null` when the state equals `defaultState`; use `JSON.stringify` comparison — safe because the state object key order is deterministic (built from the schema/`defaultState` shape, spread-preserved by `setState`).
3. **Restore-flag computation (specify):** `restored` must be computed in the lazy `useState` initializer (alongside the initial state), not in an effect, so the per-tool result-recompute effect runs exactly once with correct data.
4. **Param-name hygiene (clarify):** the hook must read only its own `s` param from `window.location.search`, ignoring any other params, and `shareUrl` must rebuild via `URLSearchParams.set('s', …)` so an already-open state URL is replaced, not duplicated.
5. **OPTIONAL — `base64-codec` Direction type:** `Direction` is currently declared locally in `Tool.tsx:6`; declare it in `state.ts` and import the type in `Tool.tsx` (one shared definition).
6. **OPTIONAL — e2e spec file:** prefer a new `apps/web/e2e/share-state.spec.ts` over editing `home.spec.ts` (Playwright picks up any file under `e2e/`; zero risk to existing specs).

## 6. Frozen implementation plan (Plan C)

### Shared contract

- `packages/core/src/url-state.ts`:
  ```ts
  export interface ToolStateCodec<S> {
    readonly defaultState: S
    serialize(state: S): string // must not throw; JSON string
    parse(raw: string): S | null // MUST NOT throw; null = invalid
  }
  export function zodStateCodec<S>(schema: z.ZodType<S>, defaultState: S): ToolStateCodec<S>
  export const STATE_PARAM_VERSION = '1' // transport envelope: s = "1.<base64url(JSON)>"
  export function parseToolState<S>(raw: string | null, codec: ToolStateCodec<S>): S
  // null | wrong version | bad base64url | bad JSON | schema failure → defaultState
  export function serializeToolState<S>(state: S, codec: ToolStateCodec<S>): string | null
  // JSON.stringify → base64url; null when JSON-equal to defaultState
  ```
- `packages/ui/src/useToolUrlState.ts`:
  ```ts
  export function useToolUrlState<S>(
    codec: ToolStateCodec<S>,
    options?: { paramName?: string }, // default 's'
  ): {
    state: S
    setState: React.Dispatch<React.SetStateAction<S>>
    shareUrl: string
    restored: boolean
  }
  ```
  Mount-lazy `useState` initializer reads `window.location.search` → `URLSearchParams.get(paramName)` → `parseToolState` (computes `restored` in the same initializer). `setState` never touches the URL. `shareUrl` = memoized `serializeToolState(state)` → `''` when null, else `new URL(window.location.href)` + `searchParams.set('s', …)`.
- The app knows **nothing** about any tool's state.
